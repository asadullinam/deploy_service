# RFC-002: Выбор базы данных и инструмента доступа к данным

**Статус:** Принято

**Дата:** 2025

## Контекст

Нужно выбрать СУБД для хранения проектов, пользователей, деплоев и данных монетизации. Текущая реализация в памяти подходит только для разработки, но не для production.

Требования:

- Реляционные данные с внешними ключами (project -> releases, project -> resource_usage)
- ACID-транзакции (критично для изменений статуса проекта)
- Простое развертывание: один сервис, без сложной топологии
- Go-совместимость

## Рассмотренные варианты

### Вариант A: PostgreSQL + sqlc

**Как работает:**
SQL-запросы пишутся вручную в `.sql`-файлах, sqlc генерирует из них типизированный Go-код.

```sql
-- query.sql
-- name: GetProjectByID :one
SELECT id, name, owner_id, status, created_at, updated_at
FROM projects WHERE id = $1;
```

```go
// сгенерированный код (не редактировать вручную)
func (q *Queries) GetProjectByID(ctx context.Context, id string) (Project, error) { ... }
```

**Плюсы:**

- SQL контролируется разработчиком - понятно что именно выполняется
- Типобезопасность на уровне компиляции: неправильное число аргументов = ошибка компиляции
- Нет N+1 проблем (они видны в SQL)
- Сгенерированные интерфейсы легко мокировать в тестах
- Минимальный runtime: только `pgx/v5`

**Минусы:**

- Нужно писать SQL явно (для некоторых - плюс)
- При изменении схемы нужно перегенерировать код (`sqlc generate`)
- Менее удобен для динамических запросов с переменным числом фильтров

**Вывод:** подходит для этого проекта: схема простая, запросы предсказуемые.

---

### Вариант B: PostgreSQL + GORM

**Как работает:**
ORM-библиотека, код работает с Go-структурами, SQL генерируется автоматически.

```go
var project Project
db.Where("owner_id = ? AND status = ?", ownerID, "active").Find(&projects)
```

**Плюсы:**

- Быстрый старт: меньше boilerplate для CRUD
- Автомиграции из структур

**Минусы:**

- Скрывает SQL: сложно понять что именно выполняется без включения логов
- Частые проблемы с N+1 для связанных данных
- Тяжелый runtime, reflection-based
- При сложных запросах все равно приходится писать raw SQL
- Debugging: `db.Debug()` для просмотра запросов - плохая практика для production

**Вывод:** не подходит. Скрытый SQL усложняет дебаг и часто приводит к лишней нагрузке.

---

### Вариант C: PostgreSQL + pgx напрямую

**Как работает:**
Прямые вызовы `pgx` без генерации кода.

```go
row := pool.QueryRow(ctx, "SELECT id, name FROM projects WHERE id = $1", id)
var p Project
row.Scan(&p.ID, &p.Name)
```

**Плюсы:**

- Максимальный контроль
- Нет зависимостей кроме pgx

**Минусы:**

- Много boilerplate: каждый запрос - ручной Scan
- Ошибки компиляции не поймают опечатки в именах колонок
- sqlc дает те же плюсы с меньшими усилиями

**Вывод:** разумная альтернатива для малых проектов. Здесь предпочтительнее sqlc из-за типобезопасности.

---

### Вариант D: SQLite + modernc.org/sqlite

**Как работает:**
Встроенная база данных, файл на диске.

**Плюсы:**

- Нет отдельного сервиса
- Проще развертывание для self-hosted

**Минусы:**

- WAL-режим необходим для конкурентных записей
- Ограниченные возможности (нет `RETURNING`, нет полноценного JSON)
- При росте нагрузки - миграция на PostgreSQL неизбежна
- В Kubernetes: PersistentVolume для файла БД = дополнительная сложность

**Вывод:** годится для одноузлового self-hosted. Для платформы это преждевременный компромисс.

---

### Вариант E: CockroachDB / PlanetScale

**Как работает:**
Распределенные SQL-базы, совместимые с PostgreSQL/MySQL.

**Плюсы:**

- Горизонтальное масштабирование
- Managed-вариант без операционных затрат

**Минусы:**

- Избыточно: платформа не достигнет нагрузки, требующей распределенной БД, в ближайшей перспективе
- CockroachDB несовместим с некоторыми PostgreSQL-расширениями
- Дороже на старте

**Вывод:** не сейчас. Вернуться, если текущая архитектура упрется в лимиты PostgreSQL.

## Принятое решение

**PostgreSQL + pgx/v5 напрямую**

### Обоснование

Схема данных в этом проекте реляционная и достаточно стабильная. Для текущего количества запросов (порядка 5-10 на store) overhead от настройки и поддержки sqlc-конфигурации не оправдывает себя. SQL остается читаемым в Go-коде, а необходимость перегенерации после каждого изменения схемы замедляла бы разработку на ранней стадии. pgx/v5 - стандарт для Go+PostgreSQL с поддержкой connection pool, named arguments, pgtype.

При желании можно мигрировать на sqlc позже - достаточно вынести SQL из Go-кода в `.sql`-файлы и добавить `sqlc.yaml`.

### Миграции

Использовать `golang-migrate/migrate` с SQL-файлами в `internal/store/postgres/migrations/`. При старте сервиса применять все миграции, которые еще не выполнены.

### Store-адаптеры

- `project_store.go` - проекты и их настройки
- `release_store.go` - релизы
- `stage_store.go` - этапы деплоя (stages)
- `user_store.go` - пользователи (JWT + balance)
- `usage_store.go` - снапшоты использования ресурсов
- `billing_transaction_store.go` - история транзакций и пополнений
- `yookassa_payment_store.go` - платежи через YooKassa

## Последствия

- Добавить зависимости: `github.com/jackc/pgx/v5`, `github.com/golang-migrate/migrate/v4`
- Добавить `docker-compose.yml` для локальной разработки с PostgreSQL
- SQL-запросы пишутся в Go-коде через pgx напрямую (без sqlc-генерации)
