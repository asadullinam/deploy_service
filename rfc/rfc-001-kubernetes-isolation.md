# RFC-001: Модель изоляции проектов в Kubernetes

**Статус:** Принято

**Дата:** 2025

## Контекст и проблема

Платформа размещает приложения разных пользователей в одном Kubernetes-кластере. Важно понять, как изолировать проекты так, чтобы:

- один проект не мог читать данные другого (сетевая изоляция),
- один проект не мог исчерпать ресурсы кластера и положить соседей (изоляция ресурсов),
- пользователь мог управлять своим окружением (доступ к kubectl) без доступа к чужому,
- стоимость инфраструктуры оставалась приемлемой на старте.

## Рассмотренные варианты

### Вариант 1: Namespace-изоляция без vcluster

Каждый проект - отдельный namespace с NetworkPolicy и RBAC.

**Как работает:**

```
Кластер
├── namespace: project-A  (NetworkPolicy: deny-all + allow-own)
│   └── pod: app-A
└── namespace: project-B
    └── pod: app-B
```

**Изоляция:**

- Сетевая: достигается через NetworkPolicy. Без явного разрешения трафик между namespace заблокирован.
- RBAC: ServiceAccount с правами только в своем namespace.
- Ресурсная: через LimitRange и ResourceQuota в namespace.

**Плюсы:**

- Минимальные накладные расходы: нет дополнительных компонентов
- Быстрое создание: `kubectl create namespace` + несколько манифестов
- Простая диагностика: один кластер, один `kubectl`

**Минусы:**

- Пользователь получает доступ к реальному Kubernetes API кластера. При ошибке в RBAC-настройках - риск эскалации привилегий.
- Нельзя дать пользователю права `cluster-admin` внутри своей зоны (таких прав нет на уровне namespace).
- Пользователь видит некоторые cluster-wide ресурсы (например, StorageClass, Node).
- Изоляция на уровне ядра (cgroups) общая - при активном использовании CPU/памяти возможен noisy-neighbor эффект без Resource Quota.

**Вывод:** подходит для раннего MVP без доступа пользователя к kubectl. Не подходит, если пользователю нужен полный kubectl-доступ к своему окружению.

---

### Вариант 2: vcluster (виртуальный кластер) на каждый проект

Каждый проект получает виртуальный Kubernetes-кластер, работающий как pod в namespace хост-кластера.

**Как работает:**

```
Хост-кластер
└── namespace: project-A
    ├── pod: vcluster-A (syncer + k3s/k8s control plane)
    │   └── виртуальный кластер:
    │       ├── Deployment: app-A
    │       └── Service: svc-A
    └── NetworkPolicy: deny-all + allow-vcluster
```

**Изоляция:**

- Сетевая: NetworkPolicy на уровне хост-namespace + виртуальная сеть внутри vcluster.
- API-изоляция: пользователь получает отдельный kubeconfig, работающий с виртуальным API-сервером. Не имеет доступа к хост-кластеру вообще.
- Привилегии: внутри vcluster пользователь может быть cluster-admin своего виртуального кластера - это безопасно.

**Плюсы:**

- Полная API-изоляция: пользователь взаимодействует только с виртуальным кластером
- Пользователь может быть cluster-admin в своем окружении - устанавливать CRD, Helm-чарты и т.д.
- Можно выдать пользователю kubeconfig для прямого доступа
- Легче обосновать безопасность: хост-кластер невидим для пользователя

**Минусы:**

- Каждый vcluster потребляет ~50-100MB RAM для control plane
- Время создания +30-60 секунд по сравнению с просто namespace
- Усложняет диагностику: два уровня API (хост + виртуальный)
- Синхронизация ресурсов между виртуальным и хост-кластером добавляет сложность

**Вывод:** разумный баланс по изоляции и стоимости для MVP. Пользователь получает рабочий kubectl-доступ к своей зоне.

---

### Вариант 3: Отдельный облегченный кластер (k3s) на каждый проект

Каждый проект - физически отдельный k3s-кластер на VM или в облаке.

**Как работает:**

```
VM-1 (k3s): project-A  ──── отдельная сеть, отдельные ресурсы
VM-2 (k3s): project-B  ──── отдельная сеть, отдельные ресурсы
```

**Плюсы:**

- Максимальная изоляция: полное разделение на уровне ядра и сети
- Noisy-neighbor исключен физически
- Легко объяснить безопасность корпоративным клиентам

**Минусы:**

- Стоимость: минимальный k3s потребляет ~512MB RAM -> при 100 проектах нужно ~50GB только для control plane
- Время создания: 2-5 минут против 30 секунд для vcluster
- Операционная сложность: управление флотом VM вместо одного кластера
- Неоправданно для малых команд и одиночных проектов

**Вывод:** слишком дорого для текущей аудитории. Возможен как корпоративный тариф в будущем.

---

### Вариант 4: GitOps с Argo CD / Flux

Желаемое состояние описывается в git-репозитории, GitOps-оператор приводит к нему кластер.

**Как работает:**

```
Git-репозиторий (состояние)
    └── projects/A/manifests/
         └── deployment.yaml
                 -> (sync)
    Argo CD -> Kubernetes
```

**Плюсы:**

- Прозрачная история всех изменений инфраструктуры
- Простой rollback: git revert
- Декларативная модель - меньше "произошло что-то, неизвестно что"

**Минусы:**

- Высокий порог входа: нужна команда, знакомая с GitOps-паттернами
- Дополнительные компоненты: Argo CD добавляет ~300MB RAM, требует настройки
- Для текущей аудитории (solopreneur) - избыточная абстракция поверх и так незнакомого Kubernetes
- Не решает проблему изоляции сама по себе - это модель управления, а не изоляции

**Вывод:** можно добавить позже как слой управления поверх выбранной модели. Это не замена вариантам 1-3.

## Принятое решение

**Вариант 2 (vcluster) для всех проектов.**

### Обоснование

Ключевая часть платформы - дать пользователю реальное Kubernetes-окружение и при этом не ломать соседей. Без vcluster это небезопасно. Целевая аудитория ожидает полный kubectl-доступ, поэтому режим "только namespace" без vcluster не реализуется - поддержка двух путей провижининга усложняла бы код и тестирование при сомнительной отдаче.

Цена по памяти (около 75MB на проект) приемлема: на 1000 проектов это ~75GB, то есть 2-3 стандартные ноды. Не все проекты активны одновременно, поэтому vcluster можно останавливать при простое.

GitOps (Вариант 4) можно добавить позже как способ управления состоянием, но он не решает изоляцию.

### Реализация

```
При создании проекта:
1. kubectl create namespace project-{id}
2. vcluster create vcluster-{id} --namespace project-{id} --driver helm
3. kubectl apply NetworkPolicy default-deny-all
4. kubectl apply NetworkPolicy allow-vcluster-control-plane
5. kubectl apply NetworkPolicy allow-gateway-controller
6. Установка Ingress NGINX внутри vcluster
7. Развертывание Grafana с доступом к Prometheus/Loki хост-кластера
```

## Решения по открытым вопросам

### 1. Kubeconfig пользователю: выдавать

**Решение:** предоставить `GET /projects/{id}/kubeconfig`, который возвращает kubeconfig для подключения к виртуальному кластеру проекта.

Обоснование: ключевая ценность платформы - полноценное k8s-окружение. Без kubeconfig пользователь не может устанавливать Helm-чарты, смотреть логи, управлять ресурсами. Это безопасно: kubeconfig ведет в виртуальный кластер, не в хост.

Механизм хранения: kubeconfig читается из Secret `vc-{vclusterName}` в хост-namespace (с ожиданием готовности до 180 секунд). Если kubeconfig содержит `localhost:8443` (ClusterIP-сервис vcluster), provisioner патчит Service на LoadBalancer, ждет получения external IP и переписывает server URL в kubeconfig с `insecure-skip-tls-verify: true`. Kubeconfig сохраняется в БД как зашифрованный текст. Ротация - по явному запросу пользователя (`POST /projects/{id}/kubeconfig/rotate`).

---

### 2. Suspend vcluster: явное действие пользователя + автоматический billing guard

**Решение:** vcluster работает пока проект `active`. Остановка возможна двумя способами:

- Явное действие пользователя через `POST /projects/{id}/suspend`, возобновление - `POST /projects/{id}/resume`
- Автоматический suspend через billing guard при исчерпании баланса:
  - Баланс <= 0 - запускается grace period (по умолчанию 24 часа)
  - Grace period истек - автоматический suspend + уведомление
  - Retention period (по умолчанию 7 дней) после suspend - автоматическое удаление проекта

Обоснование: явный контроль - основная модель, но без автоматической приостановки платформа накапливает убытки от пользователей с нулевым балансом. Grace period и уведомления (в том числе через Telegram) смягчают неожиданность для пользователя.

Новые статусы проекта:

```
creating -> active <-> suspended
            |
            v
          deleting -> deleted
```

Биллинг при suspended: CPU/память не потребляются - не тарифицируются. Хранилище продолжает тарифицироваться.

---

### 3. Resource Quota: базовые лимиты включены

**Решение:** при создании namespace устанавливать `ResourceQuota` и `LimitRange` с лимитами по умолчанию.

ResourceQuota:

```yaml
requests.cpu: "4"
requests.memory: "8Gi"
limits.cpu: "16"
limits.memory: "32Gi"
pods: "50"
```

LimitRange (значения по умолчанию для pod'ов без явных limits):

```yaml
default:
  cpu: "1"
  memory: "512Mi"
defaultRequest:
  cpu: "100m"
  memory: "128Mi"
```

Обоснование: без квот один активный проект может поглотить весь кластер и положить соседей. Квоты нужны с первого проекта в production. LimitRange гарантирует, что pod'ы без явных limits получают разумные значения по умолчанию.

Повышение лимитов - через тарифный план (в будущем).

---

### 4. Сетевой доступ: Gateway API с поддоменами

**Решение:** Gateway API на уровне хост-кластера. Один `Gateway` на кластер, каждый сервис получает поддомен по формату:

- Production: `{service-name}.{project-id}.{APPS_BASE_DOMAIN}` (например `my-svc.prj-123.apps.deploy-platform.ru`)
- Другие стейджи: `{service-name}.{project-id}.{stage}.{APPS_BASE_DOMAIN}` (например `my-svc.prj-123.staging.apps.deploy-platform.ru`)

Gateway API вводит три уровня, которые соответствуют ролям платформы:

```
GatewayClass   - инфраструктурная команда (установить один раз)
                 "контроллер nginx, вот его параметры"

Gateway        - платформа (namespace: gateway)
                 "один внешний IP, wildcard TLS"

HTTPRoute      - проект (namespace: project-{id})
                 "мой поддомен -> мой сервис"
```

Внутри vcluster приложения пользователей используют Ingress-ресурсы, которые синхронизируются на хост-кластер через `sync.toHost.ingresses.enabled=true`.

Если `APPS_BASE_DOMAIN` не задан, в качестве fallback автоматически устанавливается Ingress NGINX v1.11.2 внутри vcluster с выделенным LoadBalancer IP и доменом `{ip}.nip.io`.

**Схема (основной режим):**

```
*.apps.deploy-platform.ru
         |
    Gateway (ns: gateway)         (платформа управляет)
    allowedRoutes.from: All
         |
   +-----+-----+
Ingress         Ingress           (синхронизированы из vcluster)
(project-A)     (project-B)
   |                 |
Service-A         Service-B
```

**Конфигурация (устанавливается один раз при развертывании кластера):**

```yaml
# GatewayClass - cluster-scoped
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx
spec:
  controllerName: k8s.nginx.org/nginx-gateway-controller
---
# Gateway - в выделенном namespace
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: platform-gateway
  namespace: gateway
spec:
  gatewayClassName: nginx
  listeners:
    - name: https
      port: 443
      protocol: HTTPS
      hostname: "*.apps.deploy-platform.ru"
      tls:
        mode: Terminate
        certificateRefs:
          - name: wildcard-tls
      allowedRoutes:
        namespaces:
          from: All
```

Дополнительная NetworkPolicy `allow-gateway-controller` разрешает входящий трафик из namespace контроллера (настраивается через `GATEWAY_CONTROLLER_NAMESPACE`, по умолчанию `nginx-gateway`). Без нее `default-deny-all` блокировал бы все входящие запросы.

Требования к кластеру: Gateway API CRDs, совместимый контроллер (nginx gateway fabric, Envoy Gateway и др.), NetworkPolicy-CNI (Calico или Cilium), wildcard DNS + TLS-сертификат.

## Последствия принятого решения

- **Минимальная конфигурация хост-кластера:** vcluster (Helm), Metrics Server, NetworkPolicy-CNI (Calico или Cilium), Gateway API CRDs + совместимый контроллер, wildcard DNS + TLS.
- **Мониторинг:** Grafana автоматически разворачивается внутри каждого vcluster с доступом к Prometheus и Loki хост-кластера. Для этого создается дополнительная NetworkPolicy `allow-project-grafana-egress`, разрешающая трафик к namespace `monitoring`.
- **Биллинг:** метрики собираются на уровне хост-namespace (pods vcluster-синхронизации). Billing guard автоматически приостанавливает проекты при нулевом балансе.
- **Kubeconfig:** хранится в БД зашифрованным, выдается по запросу через API.
- **Fallback без APPS_BASE_DOMAIN:** если домен не задан, Ingress NGINX v1.11.2 устанавливается внутри vcluster автоматически, используя `{ip}.nip.io` как домен.
