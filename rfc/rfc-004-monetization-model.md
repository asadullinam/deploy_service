# RFC-004: Модель монетизации

**Статус:** Принято

**Дата:** 2025

## Контекст

Платформа потребляет реальные ресурсы кластера на каждый проект. Нужно выбрать:

- что тарифицировать,
- как считать,
- когда и как списывать деньги.

Целевая аудитория MVP: одиночные проекты и небольшие команды. Для них важен низкий порог входа - платить вперед за новый сервис обычно не готовы.

## Что тарифицировать

### Вариант A: только CPU + память

Самые понятные метрики. Пользователь может оценить размер своего приложения и прикинуть стоимость.

**Плюсы:** простота реализации и объяснения, достаточно для MVP.
**Минусы:** не учитывает хранилище и трафик - неполная картина реальных затрат.

### Вариант B: CPU + память + хранилище + трафик

Полная картина затрат.

**Плюсы:** честнее отражает реальные расходы платформы.
**Минусы:** сложнее собирать (трафик нужен egress-счетчик в CNI), сложнее объяснять пользователю.

### Принятое решение: CPU + память + хранилище + egress + dedicated LB

Все пять метрик тарифицируются:

- **CPU** - core-hour
- **Память** - GB-hour
- **Хранилище** - по PVC в namespace, GB-month
- **Egress** - через Prometheus (5 fallback-запросов для разных CNI), GB
- **Dedicated Load Balancer** - per-project выделенный LB, час

Метрики собираются `MetricsCollector` с интервалом по умолчанию 5 минут (`METRICS_COLLECTOR_INTERVAL`). Архитектура `MonetizationEngine` через интерфейс позволяет расширить без переписывания сервиса.

## Как списывать: предоплата vs постоплата

### Вариант A: Постоплата (pay-as-you-go)

Пользователь пользуется, в конце периода (месяц) выставляется счет.

**Плюсы:**

- Нулевой порог входа - не нужно вносить деньги, чтобы попробовать
- Стандарт для cloud-провайдеров (AWS, GCP, Yandex Cloud)
- Подходит для аудитории, которая еще не доверяет новому продукту

**Минусы:**

- Риск дебиторской задолженности (пользователь наработал, не заплатил)
- Нужен механизм приостановки при неоплате

**Снижение рисков:** жесткий лимит - при превышении лимита задолженности новые деплои блокируются.

### Вариант B: Предоплата (credits)

Пользователь вносит баланс, платформа списывает.

**Плюсы:**

- Нет риска неоплаты
- Проще финансовая модель (нет дебиторки)

**Минусы:**

- Высокий порог входа - нужно "положить деньги" до первого деплоя
- Сложнее конвертировать новых пользователей на незнакомом продукте

### Принятое решение: предоплата (credits)

Пользователь вносит баланс, платформа списывает в реальном времени:

- Новому пользователю начисляется стартовый баланс (`DEFAULT_USER_BALANCE_RUB`)
- Баланс можно пополнить через ЮKassa (`POST /billing/top-up/initiate`)
- Стоимость считается в реальном времени и вычитается из баланса
- При `available <= 0` запускается grace period, затем suspend

Предоплатная модель проще и безопаснее - нет риска накопления дебиторской задолженности. Стартовый баланс выполняет функцию "нулевого порога входа", которую давала бы постоплатная модель. Таблица `billing_transactions` отслеживает пополнения, списания и рефанды.

## Тарифные ставки

Валюта - рубли (целевая аудитория - российские разработчики). Все тарифы настраиваются через переменные окружения.

| Ресурс       | Единица   | Цена по умолчанию | Переменная окружения           |
| ------------ | --------- | ----------------- | ------------------------------ |
| CPU          | core-hour | 0.72 руб          | `TARIFF_CPU_CORE_HOUR_RUB`     |
| Память       | GB-hour   | 0.09 руб          | `TARIFF_MEMORY_GB_HOUR_RUB`    |
| Хранилище    | GB-month  | 45.0 руб          | `TARIFF_STORAGE_GB_MONTH_RUB`  |
| Egress       | GB        | 1.08 руб          | `TARIFF_EGRESS_GB_RUB`         |
| Dedicated LB | hour      | 0.75 руб          | `TARIFF_DEDICATED_LB_HOUR_RUB` |

Пример: приложение с 0.5 CPU и 256MB RAM, работающее 24/7 в месяц (~730 часов):

- CPU: 0.5 x 730 x 0.72 = **262.8 руб**
- Память: 0.25 x 730 x 0.09 = **16.4 руб**
- Итого: ~**279.2 руб/месяц**

## Защита от исчерпания баланса

Вместо фиксированных долларовых порогов используется механизм grace/retention, который адаптивно срабатывает при нулевом балансе:

- `available <= 0` - запускается **grace period** (по умолчанию 24 часа, `BILLING_GUARD_GRACE_PERIOD`)
- Grace period истек - **auto-suspend** всех активных проектов пользователя + уведомление
- После suspend - **retention period** (7 дней, `BILLING_GUARD_RETENTION_PERIOD`)
- Retention period истек - **auto-delete** проекта

При пополнении баланса: grace period сбрасывается, расписание удаления отменяется.

Пользователь получает уведомления на каждом этапе (через Telegram, если настроен). Billing guard проверяет балансы с интервалом 1 минута (`BILLING_GUARD_INTERVAL`).

## Период расчета

Агрегация usage snapshots - каждые 5 минут (`METRICS_COLLECTOR_INTERVAL`). Пятиминутный интервал дает более точную тарификацию (меньше "потерянного" использования между снимками).

## Последствия

- `CostBreakdown` содержит поля для CPU, памяти, хранилища, egress и dedicated LB.
- `MonetizationEngine` интерфейс расширяем - реализация за `tariff.go` + `engine.go`.
- Таблица `billing_transactions` реализована для пополнений, рефандов, списаний.
- ЮKassa интегрирована как платежный шлюз (`POST /billing/top-up/initiate`).
