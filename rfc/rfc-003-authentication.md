# RFC-003: Аутентификация и управление доступом

**Статус:** Принято

**Дата:** 2025

## Контекст

Платформа должна идентифицировать пользователей и защищать ресурсы (проекты) от доступа посторонних. Нужен механизм аутентификации для REST API, который:

- Не требует отдельного сервиса на ранней стадии
- Работает с браузером (будущий UI) и CLI/API-клиентами
- Масштабируется горизонтально (несколько инстансов сервиса)

## Рассмотренные варианты

### Вариант A: JWT (JSON Web Token) с симметричным ключом

**Как работает:**
После логина сервер выдает подписанный токен. Токен содержит claims (userID, email, exp). При каждом запросе клиент присылает токен в заголовке `Authorization: Bearer <token>`. Сервер проверяет подпись без обращения к БД.

```
Клиент                   Сервис
  |                          |
  |-- POST /auth/login ------>|
  |   {email, password}       | проверяет hash в БД
  |<--------------------------|
  |   {token: "eyJ..."}       |
  |                          |
  |-- GET /projects --------->|
  |   Authorization: Bearer   | проверяет подпись JWT
  |   eyJ...                  | (без обращения к БД)
  |<--------------------------|
  |   [{id, name, ...}]       |
```

**Плюсы:**

- Stateless: несколько инстансов сервиса не нуждаются в общем хранилище сессий
- Нет зависимости от Redis/Memcached для проверки токенов
- Стандарт для REST API, поддерживается всеми HTTP-клиентами

**Минусы:**

- Нельзя "отозвать" токен до истечения срока (если не вести blocklist)
- При компрометации - токен действителен до exp
- Размер токена больше cookie-сессии (~200 байт vs ~32 байта)

**Снижение рисков:**

- Короткое TTL (15-60 минут) + refresh token для продления
- При критических событиях (смена пароля, компрометация) - хранить blocklist в БД (только для таких случаев)

**Вывод:** хороший вариант для stateless REST API. Используется повсеместно.

---

### Вариант B: Сессии в PostgreSQL / Redis

**Как работает:**
После логина сервер создает запись сессии в БД/Redis, отдает session ID в cookie. При каждом запросе - lookup сессии.

```
POST /auth/login -> создать session в БД -> Set-Cookie: session=abc123
GET /projects    -> SELECT * FROM sessions WHERE id='abc123' -> проверить
```

**Плюсы:**

- Мгновенный отзыв: `DELETE FROM sessions WHERE id=...`
- Токен (session ID) компактный

**Минусы:**

- Каждый запрос = обращение к БД/Redis (latency + нагрузка)
- Требует sticky sessions или централизованного хранилища для горизонтального масштабирования
- Cookie работает для браузера, но неудобен для API/CLI-клиентов

**Вывод:** лишнее для текущего масштаба. Мгновенный отзыв нужен редко и решается через blocklist в JWT-подходе.

---

### Вариант C: OAuth 2.0 / OpenID Connect (GitHub, Google как провайдер)

**Как работает:**
Пользователь логинится через GitHub/Google. Платформа получает token от провайдера и создает свой JWT/сессию.

**Плюсы:**

- Пользователю не нужно создавать пароль
- Не хранить password hashes
- Для аудитории (разработчики) - GitHub аккаунт есть у всех

**Минусы:**

- Зависимость от внешнего провайдера: GitHub упал -> login недоступен
- Сложнее реализовать правильно (PKCE, state, token exchange)
- OAuth - для авторизации, не аутентификации: нужен OIDC поверх него
- Нет email/password fallback

**Вывод:** хорошее дополнение к основной auth, но не замена. Реализовать во второй итерации как "Login with GitHub".

---

### Вариант D: API Keys

**Как работает:**
Пользователь создает долгоживущий токен в UI, использует его в API-запросах.

```
GET /projects
Authorization: Bearer ds_live_abc123xyz...
```

**Плюсы:**

- Идеально для CLI и программного доступа
- Легко отозвать конкретный ключ
- Не нужен refresh flow

**Минусы:**

- Плохо для браузерного UI (долгоживущий токен в localStorage - риск XSS)
- Нужна отдельная система управления ключами

**Вывод:** уместное дополнение к JWT для CLI-доступа. Реализовать позже как `POST /users/api-keys`.

## Принятое решение

**Вариант A (JWT) как основа.** Вариант C (OAuth/GitHub) и D (API Keys) - как будущие расширения.

### Детали реализации

**Алгоритм подписи:** HS256 (HMAC-SHA256) на первой итерации. При необходимости асимметричной верификации (например, если другие сервисы будут проверять токен) - перейти на RS256.

**Структура claims:**

```json
{
  "sub": "user-123",
  "email": "user@example.com",
  "iat": 1700000000,
  "exp": 1700003600
}
```

**TTL:** access token - 24 часа по умолчанию, настраивается через `JWT_TTL`. Refresh token не реализован - при TTL 24 часа необходимость в refresh-flow минимальна. Refresh flow стоит добавить при переходе на короткий TTL или при появлении мобильных/CLI-клиентов.

**Хранение пароля:** bcrypt с `bcrypt.DefaultCost` (10 в Go).

**Маршруты:**

```
POST /auth/register   - публичный
POST /auth/login      - публичный
POST /auth/logout     - аутентифицированный (очищает cookie deploy_service_token)
```

Logout очищает cookie, но JWT остается валидным до истечения TTL. При появлении refresh token logout должен инвалидировать его в БД.

## Последствия

- Зависимость: `golang.org/x/crypto` (bcrypt)
- Таблица `users` (RFC-002)
- `JWT_SECRET` - обязательная env-переменная в production
- Все `/projects/*` маршруты защищены middleware `RequireAuth`
- OAuth/GitHub login и API Keys - не реализованы, запланированы как будущие расширения
