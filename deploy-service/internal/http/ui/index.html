С чего начать

Быстрый старт

1. Перейди во вкладку Доступ и нажми Получить KUBECONFIG_BASE64. Скопируй появившуюся строку.
2. Открой репозиторий на GitHub -> Settings -> Secrets and variables -> Actions -> создай или обнови секрет с именем KUBECONFIG_BASE64 и вставь скопированную строку.
3. Выпусти GitHub token: Settings -> Developer settings -> Personal access tokens. Нужны права Contents: Read and write и Pull requests: Read and write на репозиторий сервиса.
4. Нажми Настроить токен выше и сохрани его — или вставь прямо в поле «Временный токен» для разового деплоя.
5. Заполни форму, нажми Создать PR с деплой-конфигом — PR появится в репозитории. После мержа GitHub Actions выкатит сервис.

Вопросы

FAQ

Q Что дает тип сервиса «Публичный адрес»?
Платформа автоматически выдает внешний адрес с HTTPS и настраивает роутинг. Тип «Только внутри платформы» оставляет сервис недоступным снаружи — подходит для внутренних API и баз данных.
Q На что влияет количество реплик?
Каждая дополнительная реплика — это отдельная копия контейнера. Несколько реплик повышают устойчивость к падениям и позволяют обновлять сервис без даунтайма, но пропорционально увеличивают стоимость.

Диагностика

Что делать если не работает

1. Открой вкладку Состояние — там видно namespace, deployment и поды. GitHub Actions может показывать success, пока сервис еще не поднялся.
2. Поды есть, но Ready = 0 — проблема внутри контейнера: неверный порт, упавший процесс или не проходит readiness-проверка.
3. Подов нет вообще — скорее всего workflow применил манифесты не в тот кластер. Проверь, что KUBECONFIG_BASE64 в GitHub Secrets взят именно отсюда, из этого проекта.
4. Скачай kubeconfig и проверь вручную:
kubectl --kubeconfig ./kubeconfig.yaml get deploy,pods -n production

Как это устроено

Флоу деплоя

Вся конфигурация задается один раз через интерфейс — имя сервиса, порты, Dockerfile, контур, профиль ресурсов. На основе этих данных платформа подставляет значения в готовые шаблоны манифестов и генерирует GitHub Actions workflow. PR создается автоматически — тебе остается его смержить.

1. Заполняешь форму — репозиторий, ветка, имя сервиса, порты, тип доступа, количество реплик, профиль ресурсов.
2. Платформа собирает конфиг — значения подставляются в заготовленные Kubernetes-манифесты: Deployment, Service, HTTPRoute. Генерируется GitHub Actions workflow с шагами сборки и деплоя.
3. Создается PR — в репозитории появляется ветка с манифестами и workflow. После мержа Actions собирает образ, пушит в registry и применяет манифесты в vcluster проекта.
4. Сервис живет в изолированном кластере — каждый проект получает собственный vcluster с отдельным namespace, сетевыми политиками и kubeconfig. Контуры (production, test, staging) разделены внутри проекта.

Что конфигурируется

Разделы и манифесты

Каждый раздел интерфейса отвечает за конкретную часть манифестов. Значения из форм подставляются напрямую в шаблоны — ничего не нужно писать руками. Ниже — что именно и куда попадает.

> Деплой — здесь задается все, что попадет в манифесты: имя сервиса становится именем Deployment и Service, порты прописываются в containerPort и ServicePort, реплики — в spec.replicas, профиль ресурсов — в resources.requests и limits.
> Контуры — каждый контур (production, test и др.) деплоится в отдельный namespace внутри vcluster. Один проект может иметь несколько независимых окружений с разными версиями сервиса.
> Доступ — kubeconfig выдается на уровне vcluster проекта, не host-кластера. Именно его нужно сохранить в GitHub Secret KUBECONFIG_BASE64 — workflow использует его для применения манифестов.
> Публичный адрес — если выбран тип «Публичный адрес», платформа создает HTTPRoute и привязывает внешний домен. Адрес появляется в разделе «Обзор» после первого деплоя.

Первичная настройка

Данные проекта для деплоя

Эти данные сохраняются как постоянные настройки проекта. GitHub токен задается отдельно кнопкой «Настроить токен» на вкладке «Деплой».

Что нужно сделать перед первым PR

  1. Открой этот проект во вкладке Доступ и получи kubeconfig именно этого проекта.
  2. Если кнопка копирования недоступна, скачай kubeconfig файлом и сохрани его локально, например как demo-kubeconfig.yaml.
  3. Преобразуй содержимое файла в одну строку base64 без переносов: это и будет значение для GitHub Secret KUBECONFIG_BASE64.
  4. Открой репозиторий на GitHub: Settings -> Secrets and variables -> Actions и создай или обнови secret KUBECONFIG_BASE64.
  5. Используй kubeconfig только этого проекта. Kubeconfig host-кластера или другого проекта workflow отклонит.

Команда для Linux:

base64 -w 0 ./<project-id>-kubeconfig.yaml

Команда для macOS:

base64 < ./<project-id>-kubeconfig.yaml | tr -d '\n'

После обновления секрета можно создавать PR или перезапустить упавший workflow в репозитории.
